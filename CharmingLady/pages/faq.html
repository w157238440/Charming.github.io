常见问题 · 16 条

先把该问的问清楚，再决定要不要合作。

下面这些问题，是过去几年在邮件和会议里被问过最多的。每一条都分「结论」和「为什么」—— 结论可以直接拿去判断，理由让你看清我是不是在敷衍。

适用 · 网站 / 小程序 / 接口与部署 / 口径 · 演示性设定，以书面合同为准

01 · 合作方式

先确认边界，再谈实现。

这一组问题的共同点是：都关于「你和我各自负责到哪一步」。

结论：中小体量（单站、单小程序、单套接口）可以一个人从头做到上线；体量再往上，建议我负责主线、你补人手。

为什么：一个人做最贵的成本不是写代码，是没有人帮你查漏。我的做法是把检查清单写死——上线前必须过安全、性能、兼容、备份四项，每项都有具体条目，逐条勾掉才发版。清单在 colophon.html 里公开，你可以拿去核对。

结论：前端、后端、小程序三段都能独立交付；界面排版与信息结构我能做，插画、品牌视觉、动效长片不做。

为什么：我能保证的是「结构清楚、层级正确、窄屏不塌」，这是工程能力范围内的部分。需要强品牌表达的视觉稿，交给你或你的设计师，我按稿实现并给出可维护的组件拆分。

结论：不驻场。以远程协作为主，重要节点可以到北京当面沟通。

为什么：远程的前提是信息留痕：需求写进文档、决策写进会议记录、进度写在看板里。驻场反而容易把这些东西留在口头。若项目需要每日同步，我会固定一个 30 分钟的站会窗口。

结论：每周一次进度同步（文字 + 可点开的预览地址），有阻塞当天说，不等下周。

为什么：「等做完再给你看」是延期的主要原因。每周给一个能点开的预览，问题会在还便宜的时候暴露出来。

02 · 报价与周期

按范围报价，不按工时。

下面所有数字都是演示性设定，用来解释算法，不是报价单。

结论：按范围报价。范围在「方案与拆解」之后确定，报价单写清包含什么、不包含什么、超出部分怎么算。

为什么：按工时报价，等于把「我效率高」变成「我赚得少」，也等于把范围膨胀的风险全丢给你。按范围报价，双方都只需要盯住一件事：这份范围清单是否准确。

结论：展示型站点 2–3 周；带账号、后台、支付的项目 6–10 周；小程序首发版本 3–5 周（不含审核等待）。

为什么：时间主要不在写页面，而在「内容什么时候齐、接口什么时候通、审核什么时候过」这三件外部依赖上。范围清晰、素材齐备的项目，通常比预估快一周。

结论：三段式：启动 40% / 主体验收 40% / 上线 20%。范围变更单独确认，不混进原合同。

为什么：把最后一笔留在上线，是为了让「上线」这件事有人在后面推；把变更单独确认，是为了避免「顺手再加一个功能」把项目拖成无底洞。

03 · 技术与交付

交付的不是一堆文件，是一套能接手的东西。

这一组问题的共同点是：项目结束之后，你还能不能自己往下走。

结论：尾款结清后源码与文档全部归你，仓库直接转给你，我本地不留副本；不留后门、不留只有我知道的构建脚本。

为什么：留后门在技术上没有意义——真正的锁定靠的是「文档不写、结构不讲」。所以我的交付件里固定包含三样：结构说明、部署手册、接口约定。三样齐了，换人接手才是低成本的。

结论：可以指定，但我会先说清代价。默认组合是 Vue 3 / React + TypeScript + NestJS 或 Spring Boot + MySQL / Redis。

为什么：技术栈的选择标准只有两条：你的团队能不能接、三年后还能不能招到人。为了「新」而选一套没人维护的方案，最后买单的是你。

结论：能，但先做「体检」：读一遍关键链路，出一页结论（哪些能留、哪些必须改、改的代价）。体检按天计费，不满意可以停在体检。

为什么：直接报「重构多少钱」是不负责的。没读代码就报价，最后一定是加钱或者减范围，两种都难看。

结论：上线后 30 天内的问题免费修（不含新增需求）。之后可选按月维护，或一次性买断、由你的团队接手。

为什么：30 天是「真问题暴露完」的经验值：并发、边界数据、真实网络环境，通常在这段时间里才现形。维护期内含监控、备份检查与每月一次小改动额度。

结论：纯静态站点可以零成本跑在 GitHub Pages 上（就是本站用的方式）；需要接口与数据库时，一台低配云主机 + 对象存储通常够用。

为什么：很多项目一开始就买了过高配置的服务器，实际上线初期流量只有几十人/天。先按最小可用买，等监控数据说话再扩容，是更省的做法。

04 · 小程序专项

审核不是运气，是清单。

小程序的坑大多不在代码，而在资质、类目和授权顺序上。

结论：不能保证，但能把可控的部分做到位：类目与页面一致、隐私政策齐全、授权顺序正确、无诱导分享、无未备案域名。

为什么：审核结论由平台判定，谁都保证不了。能保证的是「不因为低级错误被驳回」。第一次提交前的自查清单会作为附件一起交付。

结论：需要已认证的小程序主体、开通微信支付商户号；涉及特定经营类目的，还要对应许可证。这些必须由你方主体申请，我不能代办。

为什么：支付与资质绑定的是经营主体，代持或借用资质既违规也会在结算环节卡死。技术侧我负责的是下单、支付、回调、退款、对账这条链路的正确性。

结论：先分包，再压图，最后才考虑砍功能。主包只留首屏必需，其余按页面路径分包、按需加载。

为什么：大多数超限不是功能太多，是图片没压、公共组件被重复打进多个分包。处理顺序错了，就容易把有用的功能砍掉，问题却还在。

05 · 隐私与授权

能让你踩坑的，都不做。

这一组问题关于素材、数据与「谁承担后果」，也是我最保守的部分。

结论：你提供的素材由你保证权利；我用的第三方素材必须可商用并登记来源（站点里每个图片来源都记在 docs/ 里）。来源不明的图一律不用。

为什么：图片侵权是最常见的「上线半年后收到律师函」的原因。为省几百块素材费去冒这个风险，不划算。

结论：只收集业务必需字段；能不留明文手机号就不留；日志里不写身份证、银行卡、完整手机号。个人信息处理规则由你方主体对外公示。

为什么：数据合规的责任主体是运营者，不是开发者。我能做的是「按最小必要原则实现」，并且把该留的删除、导出、注销接口做出来——这些是审计时最先被问到的。

结论：把它当作作品集与演示，不要当合同、报价单或技术承诺。站点里的项目、客户、数据、价格均为演示设定。

为什么：这是个人作品集站，不是经营主体对外发布的服务条款。所有可能被误读成承诺的地方，都在 disclaimer.html 里逐条写明。
