留言簿 · 本地保存 · 可检索

留一句话，比点个赞更具体。

这里没有后端。预置的示例留言写在源码里，所有访客都能看到；你当场写的那条会先存在 你自己的浏览器里，想让它出现在所有人眼前，导出 JSON 并入源码再提交一次即可。 下面把这条路一步一步写清了，也包括它做不到什么。

02 · 写留言

说具体一点，留言才有价值。

「很棒」这类话对我没有帮助；「哪个页面的哪一段让你卡住了」「哪个决定你不同意」，才是能改的东西。

隐私说明： 本页不设账号、不埋点、不调用任何第三方接口。你写的称呼与城市只用于展示， 不做统计、不画像、不外传。想删除：用下面的「清空本机留言」，或清掉浏览器站点数据。

03 · 从「我能看到」到「所有人能看到」

三步，把本机留言变成正式留言。

这一步需要你有这个仓库的提交权限；如果你只是访客，把导出的 JSON 发邮件给我也一样。

  1. 导出

    点下面的按钮下载 JSON，或直接复制到剪贴板。里面只有你本机新增的留言，不含种子条目。

  2. 并入源码

    打开 assets/js/guestbook.js，把每条对象粘进文件顶部的 SEED 数组（数组里每一项就是一条留言）。

  3. 提交并等一分钟

    提交后 GitHub Pages 会重新发布，一分钟内所有人都能在本页看到这条留言。它从此是「文件」，不再依赖任何人的浏览器。

为什么不直接做一个「大家都能写」的留言板？ 因为这需要服务端。纯静态站点（GitHub Pages）没有进程能接收请求、没有数据库能落盘； 任何在浏览器里做的「大家一起写」，最后都变成「各写各的」。下面这张表把三条路线摊开讲， 包括各自要付的代价——你可以据此判断该选哪条，而不是被一句「支持留言」糊过去。

路线 A · 就是现在这一页

能做什么
所有人都能读；任何人能写；写的内容本机永久保存、可导出
做不到
别人写的不会自动出现在你眼前，需要人工并入源码
代价
维护者要偶尔合并一次；留言有延迟
适合
个人站、作品集、流量不大但要「看着干净」的场景

路线 B · 挂第三方评论组件

能做什么
真·多人可见、有审核、有登录态
做不到
不再是「零外部依赖」；断网或对方服务挂掉，留言区直接空白
代价
引入外部域名与脚本，隐私政策要一并改；国内访问未必稳定
适合
内容型站点、能接受第三方依赖

路线 C · 自己加后端

能做什么
即时多人可见、可管理、可反垃圾
做不到
不再是纯静态；要服务器、数据库、备份、以及长期维护成本
代价
钱和时间；还要处理内容审核与合规责任
适合
有明确运营需求、留言量大的站点

04 · 边界与声明

把做不到的写在明面上。

以下每一条都可以被验证：清缓存、换浏览器、断网，各试一次就知道我说的是不是实话。

  1. 预置的 10 条留言是演示内容。 人物、城市、项目细节均为虚构，用于展示版式与检索效果，不代表任何真实评价。
  2. 本机留言不具跨设备能力。 它存在你这台设备的 localStorage 里；换设备、换浏览器、清站点数据、用隐私模式，都会看不到。 我这边也看不到——没有任何上传通道。
  3. 不做内容审核。 本页没有审核队列，因为内容根本没有离开你的浏览器。并入源码时，我会人工读一遍再提交。
  4. 不要写隐私与敏感信息。 手机号、身份证号、住址、账号密码、他人隐私，一律不要写。留言会被存进浏览器， 导出后也可能被提交到公开仓库。
  5. 不承诺回复。 留言不等于工单。需要回复的，请走 联系页的表单或邮件； 留言簿更像门口的留言板，我一周看一次。
  6. 存储可能被系统清理。 浏览器的「清理缓存」「节省空间」策略可能连 localStorage 一起清掉， 这是浏览器行为，不是页面 bug。
  7. 法律层面的整体声明见 免责声明。 本页只是它的一条具体应用：静态站点的能力边界、演示内容的性质、以及不构成任何承诺。
